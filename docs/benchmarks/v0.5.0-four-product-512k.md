# Zuicity v0.5.0, Go Juicity, and latest juicity-rs

This is a matched replay of the previous v0.4.0 local-veth campaign containing
four products:

- Packaged Zuicity v0.5.0
- Stock upstream Go Juicity v0.5.0
- Repaired Go Juicity v0.5.0 with connected-UDP OOB preservation
- Latest official `github.com/juicity/juicity-rs` build

The campaign ran on 2026-08-07 UTC. It used the exact previous environment,
comparator artifacts, mode controls, harness, CPU assignments, quality gates,
and Williams schedule. Only the Zuicity client and server artifacts changed.
This is a complete balanced common-workload comparison, but it is not the
canonical 4 MiB standard profile because latest `juicity-rs` cannot complete
that payload reliably.

## Previous candidate comparison

The previous v0.4.0 candidate medians were 1278.97 Mbps on and 737.47 Mbps off.
Packaged v0.5.0 was 10.14% lower on and 3.62% higher off. These are unpaired
cross-campaign arm comparisons, not clean causal version effects: the unchanged
Go comparator arms drifted between -3.70% and +16.01% across the two campaigns,
and candidate-on included two accepted rows near 160 Mbps.

## Method

- Topology: two fresh Linux network namespaces joined by a veth pair.
- Host: the same WSL2 Ubuntu 24.04.4 instance, Linux 6.6.87.2, AMD Ryzen 7 5800X.
- Design: the byte-identical complete eight-treatment Williams square.
- Rotations: 8.
- Accepted measured rows: 64.
- Rejected attempts retained: 6.
- Per row: 60 fresh-connect RTT, 60 persistent RTT, and 10 throughput samples.
- Throughput operation: fresh TCP connection, 512 KiB send, then full echo receive.
- Warmups: 2 transfers per row.
- Accepted throughput transfers: 640.
- CPU affinity: server 12,14; client 8,10; driver 4; echo target 2.
- GSO probes: all eight passed before measured rows.
- Inference unit: one accepted rotation-level row median.
- Quality gates: 20% pre-row CPU, 20% background CPU, up to five attempts.
- Frequency and thermal telemetry: unavailable in both generations.

`0fedd218a61a73441c04a6def3049fc3a93b998813a1131c9478e9180510733b`.
The harness manifest SHA-256 in both generations is

## Mode controls

- Zuicity on: `ZUICITY_ENABLE_GSO=1`; off: `ZUICITY_DISABLE_GSO=1`.
- Stock Go on is its shipping default: client GSO is off while server GSO is on.
- Repaired Go on: empty `QUIC_GO_DISABLE_GSO`; off: `QUIC_GO_DISABLE_GSO=true`.
- Latest `juicity-rs` on uses the unmodified Quinn default.
- `juicity-rs` off uses the unchanged official binaries plus the same hash-pinned
  external preload that denies the `UDP_SEGMENT` capability probe on both roles.

The traced probes recorded 12/12 successful segmented sends for Zuicity on,
31/31 for stock Go on, 60/60 for repaired Go on, and 27/27 for `juicity-rs` on.
Every off treatment recorded zero attempts. The stock Go trace confirmed its
shipping client-off/server-on split.

## Qualifications and limitations

- Six `juicity-rs` GSO-on attempts timed out: five warmups and one first
  throughput transfer. All are retained in `rejected.jsonl`; all scheduled rows
  obtained complete accepted replacements within the five-attempt limit.
- Five of eight `juicity-rs` GSO-on rows needed a retry. Its accepted medians are
  therefore conditioned on eventual successful completion.
- Candidate throughput was variable, with row CVs of 53.62% on and 32.44% off.
  The GSO-on rows include two accepted values near 160 Mbps; the other six range
  from 993.33 to 1473.35 Mbps.
- Latest `juicity-rs` remained highly variable, with row CVs of 189.44% on and
  93.22% off. Its persistent RTT was also bimodal.
- `canonical_balanced_campaign` is false because the standard profile payload,
  sample count, and warmups were overridden, even though position and
  first-order carryover balance both passed.
- This is a single-host WSL2/veth comparison, not WAN or physical-NIC evidence.
